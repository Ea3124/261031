# 지점별 매출 CSV 작업 메모

## 목표와 현재 근거

`branch, amount, status, transaction_id` 열이 있는 CSV에서 지점별 매출 합계와 빈 값 처리 기록을 준비한다. 결과를 검토할 사람, 금액 단위·대상 기간, 제출 형식·경로는 현재 전달받은 내용에 없다. 확인 가능한 과제 안내에서 먼저 찾고, 남은 항목만 확인한다. 요청 범위는 자료 정리와 제출물 준비다.

현재 근거는 요청에 적힌 과제 안내 요약과 업무 담당자 답변 “취소 건은 빼세요”다. 이 답변으로 **취소 거래를 합산에서 제외한다는 방향만 확정**됐다. 실제 취소 status 값, 금액 누락, 중복 ID, status 누락을 어떻게 처리할지는 답하지 않았다.

현재 저장소의 `docs/intent.md`는 실제 과제 정보를 채우기 전의 틀이다. 과제 README와 CSV는 확인되지 않아 실제 행 수·status 값·예외 건수·지점별 합계는 아직 조사하거나 계산하지 않았다. 요청에 등장한 예외가 있다는 사실과 실제 파일 검사 결과를 구분한다.

## 지금 먼저 확인할 것

1. 실제 과제 안내·제공 자료에서 제출물의 형식·필수 경로, 합계의 금액 단위·기간, 대상 파일과 종료 시각을 찾는다. 작성되어 있으면 그대로 사용하고 다시 묻지 않는다. 기존 계산 코드가 있다면 현재 처리 방식도 읽되 이를 업무 정답으로 간주하지 않는다.
2. CSV가 제공되면 원본을 보존한 상태에서 인코딩·구분자·헤더·행 수와 파싱 가능 여부를 확인한다. 원본 행 번호를 붙여 결과와 예외 기록을 원본까지 추적할 수 있게 한다.
3. `status`의 실제 값과 공백 형태, `amount`의 숫자 형식·빈 값·변환 실패를 조사한다. `branch`와 `transaction_id`에도 빈 값이 있는지 확인한다. 공백 정리 전 값과 정리 후 값을 구분하고, 지점명이나 상태값을 임의로 합치지 않는다.
4. 중복 ID별로 모든 열이 같은 중복과 지점·금액·status가 서로 다른 중복을 나눈다. 특히 같은 ID에 취소와 다른 상태가 함께 있는지, 빈 값 문제가 겹치는지 확인한다. 파일 순서가 갱신 시각이라는 가정은 하지 않는다.
5. 예외별 원본 행 목록과 겹침을 기록한다. 한 행이 금액 누락·status 누락·중복에 동시에 걸릴 수 있으므로 항목별 건수를 더한 값을 전체 예외 행 수로 쓰지 않는다.

위 조사는 아직 수행 예정이다. 발견하지 않은 값·건수나 데이터 손실을 조사 결과처럼 쓰지 않는다.

## 메신저 질문 초안

업무 판단은 이미 답변한 업무 담당자에게 이어서 확인한다. 아래는 사람이 검토해 보낼 초안이며 **실제 전송 여부는 모두 미확인**이다. 에이전트가 메신저 입력·전송·화면 조작을 하지 않는다.

> 취소 거래는 합계에서 제외하는 것으로 이해했습니다. 매출 합계와 빈 값 처리 기록을 맞추려면 아래 기준이 더 필요합니다. 실제 파일을 확인한 뒤 해당 status 값과 원본 행 예시를 붙여 질문하겠습니다.
>
> 1. 어떤 status 값을 취소로 보면 될까요? status가 빈 행은 유효 거래로 포함할지, 확인 전까지 보류할지 알려주세요. 빈 상태를 포함하거나 제외하면 지점별 합계가 달라집니다.
> 2. 금액이 빈 행은 금액을 보완받아 반영할까요, 합계에서 제외하고 누락으로 기록할까요, 아니면 업무상 0으로 처리할까요? 0 처리와 제외는 합계가 같을 수 있어도 처리 기록의 의미가 다르므로 기준을 확인하려고 합니다.
> 3. 같은 transaction_id는 전체 파일에서 하나의 거래를 뜻하나요, 지점마다 별도일 수 있나요? 동일 ID 행을 모두 합산할지, 한 거래로 볼지 확인 부탁드립니다. 한 거래라면 내용이 완전히 같은 중복과 금액·지점·상태가 다른 중복 각각에 적용할 기준도 필요합니다. 특히 취소와 다른 상태가 함께 있으면 거래 전체를 제외할지, 특정 행을 채택할지에 따라 결과가 달라집니다. 현재 열에는 갱신 시각이 없어 최신 행을 임의로 고를 수 없습니다.

실제 파일에 상태 설명이나 ID 정의가 있으면 해당 질문을 줄이고, 충돌하거나 정의가 없는 부분만 남긴다. 완전히 같은 중복과 내용이 다른 중복은 각각 짧은 원본 행 예시를 붙여 한 번에 답하기 쉽게 한다.

제출 형식·경로가 안내에도 없으면 별도로 “지점별 합계와 빈 값 처리 기록의 제출 형식·위치를 확인 부탁드립니다”라는 초안을 준비한다. 환경에 실제 제공된 안내 문의 경로가 있을 때 그 경로를 사용하도록 안내하며, 없는 지원 창구를 만들지 않는다. 담당자에게 이미 확인된 필수 제출물의 필요성을 다시 묻지는 않는다.

## 질문 상태와 답변의 영향

| ID | 근거와 미결 항목 | 받은 답변·전달 상태 | 달라지는 처리와 확인할 검사 |
|---|---|---|---|
| Q1 | 요청의 “취소 건은 빼세요”; 실제 취소값과 빈 status 처리 미정 | 취소 제외 방향만 확인됨. 추가 질문 전송 미확인 | 승인된 취소값은 합계에서 빠지고, 빈 status 행은 답변한 규칙대로 처리되는지 검사 |
| Q2 | 요청의 금액 빈 행; 보완·제외·0 처리 미정 | 답변 없음. 초안 준비, 전송 미확인 | 원래 빈 값이었음을 보존하고, 합계와 처리 기록이 선택한 규칙에 일치하는지 검사 |
| Q3 | 요청의 중복 ID; ID 유효 범위·중복 채택 규칙·취소 충돌 처리 미정 | 답변 없음. 초안 준비, 전송 미확인 | 완전 중복, 내용 충돌, 지점 간 동일 ID, 취소와 정상 상태가 겹친 사례를 각각 검사 |
| Q4 | 요청에는 금액 단위·기간·제출 형식·경로 없음 | 먼저 실제 안내 조사. 안내에 없을 때 질문 준비 | 합계 표의 단위·대상과 제출물이 안내에 일치하는지 확인 |

답변이 “빈 금액은 빼세요”만 오면 Q2의 해당 범위만 확정한다. Q1과 Q3를 해결로 표시하지 않고, 빈 금액을 제외했을 때 중복 ID의 다른 행 채택에도 영향이 있는지 필요한 질문을 좁힌다.

## 답을 기다리면서 진행할 일

- 파일을 받으면 위의 형식·분포·예외 조사를 진행한다. 원본 행별로 발견한 문제를 여러 개 기록하고, 처리는 `미결` 상태로 둔다. 중복 삭제나 빈 값 대체는 하지 않는다.
- 지점별 합계 표의 구조와 처리 기록의 구조를 준비한다. 처리 기록에는 원본 행 번호, 거래 ID·지점, 문제가 있는 열, 원래 값, 적용 규칙과 근거, 조치, 합계 반영 여부를 연결한다. 필수 파일명은 안내에서 확인하기 전 임의로 확정하지 않는다.
- 원본을 변경하지 않는 파싱·숫자 검증·예외 탐지 절차를 준비한다. 업무 규칙을 입력받아 계산할 구조는 만들 수 있지만, 미답변 규칙을 기본값으로 숨겨 실행하지 않는다.
- 확정된 산술 부분은 가상 최소 입력으로 검사할 수 있다. 예를 들어 서로 다른 ID의 유효 거래 두 행을 한 지점으로 묶어 합산하는 예시는 준비하되, 단위·유효 상태 정의가 실제 업무에서 확인되기 전 전체 매출 검증으로 표시하지 않는다.
- 실제 파일에서 모든 적용 조건이 확인된 행에 대해 부분 집계를 하더라도, 미결 행과 그 이유를 함께 붙이고 `부분 집계·최종 합계 아님`을 표시한다. 예외와 충돌하는 행은 최종 포함·제외를 결정하지 않는다.

## 답변 후 진행과 완료 기준

확인된 기준과 실제 답변 내용을 질문 ID에 연결한 뒤 적용할 순서를 정한다. 중복 정리와 취소 제외의 순서가 결과에 영향을 주면 그 순서도 합의에 포함한다. 그다음 원본에서 다시 실행해 지점별 합계와 빈 값 처리 기록을 같은 기준으로 만든다.

검사는 승인된 규칙마다 작은 입력과 독립적으로 계산한 기대 결과를 사용한다. 정상 거래, 취소, 금액 빈 값, 빈 status, 완전 중복, 내용 충돌 및 예외가 겹친 행을 다룬다. 각 원본 행의 처리 상태가 설명되고, 합계 표와 행별 반영 기록이 맞으며, 지점 합계들의 합이 최종 반영 거래 총액과 맞는지 확인한다. 건수 대조에서는 예외의 중복 집계와 중복 행의 대표 거래 연결을 구분한다.

현재 상태는 **요구 정리·질문 초안 준비 완료, 실제 CSV 검사·질문 전달·추가 답변 수신·최종 집계·제출은 미실행**이다. 다음 행동은 실제 과제 안내와 원본 CSV를 확인해 질문에 필요한 상태값·중복 유형·행 예시를 채우는 것이다. 답변이 오지 않으면 미결을 그대로 남기며 최종 매출 합계를 확정하지 않는다.
