# 공통 실행 절차

새 에이전트는 이 문서를 위에서 아래로 따른다. 과제별 코드와 명령만 달라지며 설치·맵·검증·커밋·인계 절차는 같다.

## 0. 시작 상태 확인

실제 과제 README, 안내, RULE.md, AGENTS.md를 읽는다. 제출 파일명·경로·실행 명령·금지 도구·AI 지원 종료 경계를 work/intent.md에 기록한다. 경로를 임의로 정하지 않는다.

다음 명령을 실행하고 현재 Git 상태를 확인한다.

~~~sh
git status --short
git log -1 --format=%H
python3 kit.py doctor
python3 kit.py status
~~~

커밋이 아직 없거나 검증 기록이 없으면 그 사실을 기록한다. 기존 변경을 지우거나 다른 프로젝트의 대화·개인 설정을 읽지 않는다. 앱 설정 미완료는 아직 검증할 수 없다는 뜻이다. kit.py doctor는 구조·설정·맵만 점검하며 앱 doctor 명령을 실행하지 않는다. 실제 실행 환경의 준비 여부는 kit.py check에서 확인한다.

## 1. 의도와 성공 기준 고정

work/intent.md에 다음 항목을 작성한다.

- 문제 상황과 사용자의 실제 작업.
- 필수 요구사항, 시간·환경·모델·자료·제출 제약.
- 구현할 범위와 이번에 다루지 않을 범위.
- 요구사항별 구체적인 입력과 관찰할 결과.
- 항상 지켜야 할 비즈니스 불변식.
- 검증할 사용자 인터페이스와 에이전트가 확인할 수 없는 화면.
- 완료 조건, 남은 위험, 종료 시점.

목표를 바꾸는 요청이 오면 변경 이유와 영향을 기록하고 관련 맵·검사를 수정한다. 이전 검증 결과를 새 의도에 자동 승계하지 않는다. 검증이 어려워서 목표를 낮추지 않는다.

## 2. 첫 구현과 검증 명령

기존 앱이면 관련 진입점·저장 상태·호출 경계를 읽는다. 처음 만드는 앱이면 핵심 사용자 흐름 하나와 자료형을 정하고 최소 동작을 만든다.

verification/project.json에 다음 형식으로 명령을 등록한다. 아래는 구조 예시이며 그대로 복사하면 실제 파일이 없으므로 실패한다.

~~~json
{
  "schema_version": 1,
  "doctor": {
    "argv": ["python3", "verification/doctor.py"],
    "timeout_seconds": 10
  },
  "checks": [
    {
      "id": "syntax",
      "kind": "static",
      "argv": ["python3", "verification/syntax.py"],
      "timeout_seconds": 10
    },
    {
      "id": "business-invariants",
      "kind": "business",
      "argv": ["python3", "verification/invariants.py"],
      "timeout_seconds": 20
    },
    {
      "id": "create-runtime",
      "kind": "runtime",
      "argv": ["python3", "verification/drive.py"],
      "timeout_seconds": 30
    }
  ],
  "cleanup": {
    "argv": ["python3", "verification/cleanup.py"],
    "timeout_seconds": 10
  },
  "env": {},
  "required_env": [],
  "run_timeout_seconds": 120
}
~~~

- doctor는 필요한 인터프리터·앱·초기 데이터·검사 전제조건을 확인한다. 단순히 명령 파일이 존재하는지만 보지 않는다.
- static은 실제 언어의 문법·타입·스타일 등 적합한 검사를 수행한다. 모든 언어에 같은 도구를 가정하지 않는다.
- business는 비즈니스 불변식과 실패 입력을 실제 코드로 확인한다.
- runtime은 CLI·HTTP·파일 등 사용자가 접근하는 실제 경로를 실행한다. 독립된 요구사항에서 기대 결과를 정하고 저장·재조회 등 부수효과도 확인한다.
- cleanup은 앱 doctor 또는 검사 명령을 실행하기 시작한 뒤에는 성공·실패 모두에서 실행된다. 설정·맵·stage·민감정보 사전검사에서 거절되어 앱 명령을 시작하지 않았다면 cleanup도 호출하지 않는다. 직접 만든 임시 상태와 프로세스만 정리하며 KIT_RUN_DIR의 증거를 지우지 않는다.
- 각 명령은 동기적으로 끝나야 한다. 서버가 필요하면 runtime용 검사 코드가 subprocess로 시작하고 준비 상태를 확인한 뒤 실제 요청을 보내며 finally에서 자신이 시작한 프로세스만 종료한다.
- 테스트 데이터·난수 시드·시간대·로캘·버전을 고정한다. 실제 포트는 OS가 정하도록 할 수 있으나 준비 확인과 연결에는 그 실제 포트를 사용한다.
- 필요한 비밀 값은 required_env에 이름만 적고 제공 환경에서 읽는다. 값은 파일이나 argv에 쓰지 않는다.\n- KIT_RUN_DIR, TMPDIR, TZ, PYTHONHASHSEED, PYTHONDONTWRITEBYTECODE는 실행기가 관리하므로 env와 required_env에 넣지 않는다. 고정 환경은 실행기가 제공한다.
- 검증 도중 의존성을 설치하거나 소스·문서·Git 인덱스를 수정하지 않는다. 산출물은 KIT_RUN_DIR 아래에 쓴다.

단위·속성·통합 검사는 문제에 맞춰 조합한다. 불변식 테스트가 형식 증명과 같은 것은 아니다. 프로파일·힙·부하 도구는 실제 성능 요구가 있을 때만 선택하고 버전·입력·반복 횟수·기준값을 함께 남긴다.

## 3. 앱 검증 스킬 완성

.agents/skills/verify-app/SKILL.md를 앱에 맞게 고친다. 다음 다섯 항목에 실제 명령과 기대 출력을 적는다.

1. 실행: 시작 명령, 초기 데이터, 실행 위치, 사용 포트·데이터 경로.
2. 준비 확인: 사용할 인스턴스가 올바른 앱·버전·상태인지 확인하는 명령.
3. 조작: 사용자 경로별 정확한 입력과 응답 확인 명령. 화면 경로는 응시자가 직접 확인할 절차로 구분한다.
4. 증거: 입력·출력·부수효과·로그의 저장 위치와 성공 조건.
5. 정리: 자신이 만든 프로세스·상태를 없애는 방법과 증거 보존 확인.

가이드만 쓰고 실행하지 않으면 초안이다. 최소 한 기능을 처음부터 끝까지 실제 실행하고 정리 후 증거가 남았는지 읽어 확인한다.

## 4. 기능 맵 생성·수정

정본은 .agents/skills/verify-app/features/F001.md 형태다. 파일 하나에 사용자 기능 하나를 둔다.

metadata의 필수 항목은 id, title, sources, entry, action, expected, invariants, checks, precondition이다. map add가 metadata와 사람이 읽는 본문을 같은 값으로 작성한다. 본문만 따로 고치지 말고 같은 ID의 map add로 갱신한다.

~~~sh
python3 kit.py map add --id F001 --title "실제 사용자 기능" \
  --source app/main.py \
  --entry "실제 실행 명령 또는 HTTP 경로" \
  --precondition "초기 데이터와 사용자 권한" \
  --action "정확한 입력과 수행 순서" \
  --expected "독립적으로 판단할 관찰 결과와 부수효과" \
  --invariant "이 흐름에서 항상 유지할 조건" \
  --check create-runtime
python3 kit.py map sync
python3 kit.py map check
~~~

sources에는 실제 존재하는 프로젝트 내부 소스를 적는다. checks에는 project.json에 등록된 검사 ID를 적고 기능마다 runtime 검사를 하나 이상 연결한다. 실행하지 않은 버튼·DOM 경로는 검증했다고 적지 않는다.

새 기능은 다음 F ID를 부여한다. 기존 기능의 동작 변경은 같은 ID를 갱신한다. 삭제는 해당 파일을 제거하고 map sync한다. 구조적 연결 검사만으로 문서 내용의 진실이 증명되지는 않으므로 변경 소스와 맵을 읽고 관련 실제 검사를 수행한다.

## 5. 한 작업단위의 고정 반복

다음 절차를 반복한다.

1. 작업 시작 전에 begin으로 단위 ID와 관찰 가능한 목표를 고정한다.
2. 해당 단위만 구현하거나 수정한다.
3. 관련 기능 맵·work/intent.md·work/decisions.tsv를 갱신한다.
4. 전체 변경을 stage하고 실제 diff를 읽는다.
5. commit을 시도한다. pre-commit이 iterate --staged를 실행한다.
6. 성공하면 Git의 실제 SHA와 status를 확인한 후 다음 단위를 시작한다.
7. 실패하면 마지막 보고서와 로그를 읽는다. 같은 단위에서 원인을 수정하고 다시 stage한 뒤 commit한다.

~~~sh
python3 kit.py begin --unit U001 --goal "구체적인 사용자 결과" --minutes 10 --max-attempts 3
git add -A
git diff --cached --stat
git diff --cached
git commit -m "이번 단위의 변경 이유"
python3 kit.py status
git log -1 --format=%H
~~~

훅은 문서나 코드를 고치거나 자동 stage하지 않는다. 검사 대상과 커밋 대상이 달라지는 부분 stage는 거절한다. 커밋 훅은 로컬 편의 장치이며 임의 악성 코드까지 가두는 샌드박스는 아니다.

check는 단발 검증이다. iterate는 현재 단위의 예산 안에서 check를 한 번 수행하고 재시도 상태를 남긴다. 에이전트가 코드를 고쳐 다음 iterate를 실행한다. 실행기는 AI 호출·자동 수정·자동 커밋·대기 데몬을 만들지 않는다. 실행 환경에 /loop가 있으면 이 절차를 이어가는 용도로 사용할 수 있지만 필수 의존성은 아니다.

## 6. 실패 처리와 종료

| 실패 종류 | 다음 행동 |
|---|---|
| 앱 동작·불변식 실패 | 같은 입력으로 재현하고 최초의 잘못된 상태를 만드는 코드를 수정 |
| 기능 맵 누락·소스/검사 참조 오류 | 실제 소스를 확인해 같은 ID의 맵 갱신 후 sync |
| 환경·준비 확인 실패 | 앱 수정 전에 실행 버전·데이터·필수 환경 확인 |
| 검증 도구 자체 결함 | 독립된 기대 결과로 도구를 고치고 의도적 실패도 탐지하는지 확인 |
| 시간초과·잔여 프로세스 | 보고서·정리 결과를 읽고 자기 프로세스의 생존 여부를 확인 |
| 민감정보 발견 | 커밋에서 제거하고 로그·증거에도 남지 않았는지 확인. 공개된 키면 사용자에게 사실 전달 |
| 한도 도달·금지 도구만으로 가능한 작업 | 검증 기준을 낮추지 말고 미완료로 인계 |

단위 기본값은 10분·3회이고 전체 검사 기본 상한은 120초다. 과제의 비용에 맞춰 단위 시작 전에 정한다. 실패 후 같은 작업의 예산을 초기화해 계속 돌리지 않는다. 과제 전체는 실제 종료 시각을 우선하며 종료 전에 인계·제출 안내 시간을 남긴다.

## 7. 인계와 다음 세션

work/handoff.md에 다음 내용을 기록한다.

- 원래 목표와 마지막 의도 변경.
- 현재 브랜치·마지막 SHA·커밋되지 않은 변경.
- 구현 구조와 중요한 자료형·저장 위치.
- 실행·검증 명령과 마지막 결과.
- 증거 경로와 실제 검증한 범위.
- 미확인 화면·성능·외부 의존성·남은 위험.
- 다음에 수행할 정확한 명령 또는 수정 한 가지.

다음 에이전트는 이 파일만 믿고 성공을 선언하지 않는다. Git 상태와 status를 다시 확인하고 실제 앱 준비 확인과 python3 kit.py check를 수행한다. status는 파일 내용에 대한 과거 증거의 유효성만 확인하며, 새 세션의 실행 환경까지 증명하지 않는다. 파일이 같아도 환경·외부 상태가 달라질 수 있으므로 새 세션에서는 실제 검증을 다시 실행한다. 인계 문서가 최종 커밋 뒤에 바뀌었다면 그 문서도 정상 훅을 거쳐 커밋하고 최종 SHA를 최종 응답에 남긴다. 자기 자신의 최종 SHA를 같은 커밋 본문 파일에 넣으려는 순환은 만들지 않는다.
