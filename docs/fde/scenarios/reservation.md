# 준비용 시나리오 2 — HTTP 재고 예약

키트 절차의 실제 검증용 합성 과제다. 실제 화면은 만들거나 조작하지 않는다.

## 사용자 요구

Python 표준 라이브러리로 HTTP 재고 예약 서비스를 만든다. 재고 초기값은 2다. 준비 상태·재고 조회, 예약, 예약 취소를 제공한다. 서버는 0.0.0.0에 바인딩하고 실제 포트를 출력한다. 테스트는 자신이 시작한 서버의 실제 포트에만 로컬 요청을 보낸다.

예약 요청 ID를 같은 내용으로 재실행하면 중복 예약하지 않는다. 같은 ID의 다른 내용 재사용은 오류다. 재고를 초과한 예약은 거절한다. 같은 예약의 취소를 반복해도 재고를 두 번 복원하지 않는다. 재고는 0 이상 2 이하다.

## 고정 인수 시나리오

1. 별도의 임시 상태에서 서버를 시작하고 준비 상태를 확인한다.
2. 요청 r1로 한 개 예약하면 재고 1과 예약 ID가 반환된다.
3. 같은 r1을 반복하면 같은 예약 ID와 재고 1이 유지된다.
4. 요청 r2로 한 개 예약하면 재고는 0이다.
5. 요청 r3 예약은 실패하고 재고는 0이다.
6. r1 예약을 취소하면 재고는 1이다.
7. 같은 취소를 반복해도 재고는 1이다.
8. 잘못된 요청·없는 예약 ID가 정상 상태를 바꾸지 않음을 확인한다.
9. 검사 성공·실패 후 서버 프로세스가 남지 않고 증거는 남는지 확인한다.

## 수행 계약

빈 독립 Git 프로젝트에 키트를 install한다. 기능 맵은 조회·예약·취소 3개 이상이다. runtime harness가 서버 실행→준비 확인→실제 HTTP 요청→상태 관찰→finally 종료를 소유한다.

정상 커밋 후 중복 취소가 재고를 두 번 복원하는 회귀를 잠시 도입한다. stage 후 커밋 차단과 HEAD 유지를 확인하고, 원인을 수정해 같은 작업단위에서 커밋한다. 검사 코드를 약화하지 않는다.

잘못된 기능 맵 참조와 STALE 증거를 한 번씩 탐지하고 복구한다. 화면 확인까지 했다고 보고하지 않는다. 마지막에 인계 문서·증거·서버 종료 증명을 남긴다.
