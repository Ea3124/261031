A NARRATIVE SCENARIO — NOT A BUILT-IN APP

아래는 “CLI 재고 예약” 과제를 받았다고 가정한 180분 흐름입니다. 앱 코드는 이 저장소에 없습니다. 예제를 다시 설치하는 것이 아니라, 공통 파일을 실제 문제에 어떻게 연결하는지 설명합니다.

최초 설치는 한 번만 합니다. 이후 반복은 작은 구현 → 같은 방법으로 검증 → 코드·증거 함께 스테이징 → 커밋입니다. 인계는 마지막 검증 전에 작성합니다.

전체 파일 백과

파일 하나마다 “왜 있는가 → 언제 쓰는가 → 실제로 무엇을 하는가 → 어디까지 보장하는가”를 설명합니다. 번호별 스킬과 현재 파일만 색인합니다. 과거 증거는 해당 버전의 기록으로 구분합니다. 텍스트 원문은 이 HTML 안에 들어 있어 네트워크 없이 확인할 수 있습니다.

작은 루프가 지키는 것

01 · INSTALLATION

setup.sh와 scripts/setup의 차이

setup.sh는 다른 과제 폴더에 파일을 설치합니다. scripts/setup --check는 기존 훅 충돌을 사전에 읽고, scripts/setup은 로컬 훅 경로만 연결합니다.

설치는 업데이트·앱 실행·네트워크·자동 커밋을 포함하지 않습니다. 과제 README·문서·어댑터를 보존하고 readme.kit.md·readme.skill.md를 별도로 설치합니다. 다른 공통 코드와 구버전 스킬이 있으면 비교 후 정리를 요청합니다.

02 · CONTROL

문제별 검사는 한곳에

verification/check가 초기화·실행·관찰·정리의 실제 명령을 가집니다. 공통 scripts/check는 그 검사를 실행해 소스 식별자와 로그·영수증을 남깁니다.

같은 초기 상태와 같은 명령이 필요합니다. 난수·시간·버전·외부 의존성은 문제가 요구하는 범위에서 고정합니다.

03 · COMMIT CONSISTENCY

세 내용이 같아야 커밋

작업 내용의 트리
    = 스테이징 내용의 트리
    = 통과 영수증의 tree

최신 실행 = stage된 최신 증거
status = PASS / exit_code = 0

훅은 앱 검사를 다시 돌리지 않습니다. 검사 뒤 소스·문서를 바꾸면 다시 검증합니다. 증거 자체도 최신 실행 폴더 전체가 stage돼 있어야 합니다.

04 · TRUST BOUNDARY

정확성은 해시가 대신하지 않음

잘못된 기대값·exit 0만 하는 어댑터·위조한 영수증도 해시만으로는 판단하지 못합니다. 실제 입력과 상태를 독립 기대값에 비교하고, 핵심 로직을 하나씩 깨 탐지 능력을 확인해야 합니다.

ignored 입력·환경·의존성·외부 DB는 Git 트리 밖입니다. 일반 테스트 통과는 전체 상태 공간의 형식 증명이 아닙니다.

WHAT DOES NOT RUN AUTOMATICALLY

알고 있어야 할 현실적 한계

  1. 스킬은 지침입니다. Markdown이 실제 검사를 자동 생성하거나 실행하지 않습니다. .agents 경로의 선택·주입은 사용 환경의 안내를 따라야 합니다.
  2. 기능 맵도 문서입니다. 변경 때 관련 항목을 갱신하도록 안내하지만 의미를 판단하는 자동 검사기는 없습니다. 코드·실제 사용자 경로와 대조합니다.
  3. 설치기는 업그레이드 엔진이 아닙니다. 다른 공통 파일을 자동 덮어쓰지 않습니다. 복사 중 운영체제 오류에 대한 전체 롤백도 제공하지 않습니다.
  4. 훅은 절차 통제입니다. 허위 기대값과 악성 스크립트를 차단하는 보안 샌드박스·원격 증명·전자 서명이 아닙니다. scripts/setup의 .git/config 설정 자체도 Git 소스 트리 밖입니다.
  5. 서버·시간 제한·정리는 문제별 책임입니다. 공통 래퍼가 모든 프로세스를 찾거나 앱 상태를 되돌려 주지 않습니다.
  6. Git 범위 밖 입력이 있습니다. ignored 파일·외부 DB·의존성·환경은 고정/기록하지 않으면 세션마다 달라집니다.
  7. 로컬 커밋 중심입니다. 원격 CI·watch-pr·/loop 감시자가 자동 실행되는 구조가 아닙니다. .githooks/pre-push는 실수 방지이며 실전 push 자체를 시도하지 않습니다.
  8. 시험한 범위만 주장합니다. API 성공은 화면 성공이 아니고, 불변식 테스트는 전체 프로그램 형식 증명이 아닙니다. 실전 화면 조작과 제출은 RULE의 사람/에이전트 경계를 따릅니다.

readme.skill.md에 각 역할과 상황별 흐름 다섯 가지가 있습니다. 번호는 지침을 찾는 표시이며 매번 일곱 단계를 모두 호출하는 순서가 아닙니다. 원본 비교가 필요하면 고정 외부 링크와 두 MIT 고지를 확인합니다.

설치 방식은 JinwooKim-git/cofa-kit의 setup.sh를 읽고 현재 폴더에 복사·기존 파일 보존 개념을 독립 구현했습니다. 읽은 Git blob은 b75bbaefe369b3d8698d8b9abc016676ce2b6628입니다. 해당 원본 스크립트는 실행하지 않았습니다.

pstack 출처의 고정 SHA는 25abb38559ddbabec563646224d09eff9a250eca입니다. 61개 스킬을 검토해 7개 한국어 지침으로 편집했습니다. 현재 설명서에는 그 원본 파일을 내장하지 않습니다. 출처는 고정 외부 링크로 남기고, 시작 스킬은 cofa-triage의 문제·질문 관점을 우리 방식으로 새 문장으로 작성했습니다. 과거 해시·검토 기록은 이력으로만 보존합니다.

현재 코드·번호별 스킬·안내서와 증거 파일만 각 경로별로 설명합니다. vendor 원문과 이전 HTML의 원문 사본은 삭제했습니다. 일상 과제에서 과거 증거 전체를 읽거나 실행할 필요는 없습니다. .git 내부·ignored 캐시·사용자의 개인 설정은 저장소 파일 설명 범위 밖입니다.
