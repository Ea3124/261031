# COFA 과제 작업 키트

과제 환경에서 이 문서 하나를 읽고 필요한 스킬을 만들거나, 함께 제공된 `setup.sh`로 같은 스킬을 생성한다. 저장소에는 `readme.kit.md`, `setup.sh`, `RULE.md` 세 파일만 둔다. 실제 과제의 코드·데이터·README와 스킬 생성 후 작성할 작업 기록은 과제 프로젝트에 둔다.

동봉된 `RULE.md`는 이전에 정리한 실전 운영 지침을 복원한 것이다. 시작할 때 읽되, 이번 과제의 실제 안내와 기존 프로젝트 규칙을 우선한다.

## 1. 우리가 합의한 작업 흐름

**과제·데이터 확인 및 담당자 문답 → 간결한 PRD → 최소 아키텍처 → 핵심 흐름 구현 → 최종 검증과 정리**로 진행한다. 각 핵심 단계 직후 **작은 검증 → 사용자에게 역질문 한 개 → 답변에 따른 짧은 보완**을 반복한다. 마지막에 몰아서 이해를 확인하지 않는다.

| 단계 | 남겨야 할 결과 | 단계 직후 확인할 내용 |
| --- | --- | --- |
| 과제·데이터 확인 및 DM | 목표, 데이터 의미, 확인된 답변, 미결 질문 | 주 사용자와 해결할 결정이 분명한가? |
| PRD | 필수 기능, 제약, 우선순위, 구체적인 완료 조건 | 어떤 입력에서 어떤 결과가 나와야 하는가? |
| 아키텍처 | 데이터→계산→저장→화면의 경로와 입출력 계약 | 조건 하나가 바뀌면 어느 부분이 달라지는가? |
| 핵심 계산과 화면 구현 | 실제 데이터로 작동하는 사용자 흐름 | 작은 실제 입력의 결과를 직접 설명할 수 있는가? |
| 검증과 수정 | 기대값·실제값·실행 근거·남은 한계 | 무엇을 확인했고 무엇은 아직 확인하지 못했는가? |

문답은 처음 한 번으로 끝나지 않는다. 구현이나 검증에서 새로운 업무 조건이 발견되면 담당자에게 다시 묻고 PRD·설계·검사를 함께 갱신한다. 작은 구현 오류는 해당 부분만 수정하고 재검증한다.

역질문은 사용자의 이해 점검이다. 매번 다음 작업의 승인을 받는 절차가 아니다. 답변을 기다리는 동안 확정된 조건에 관한 독립 작업은 계속할 수 있다. 사용자 답변 없이 이해했다고 기록하거나, 정답을 먼저 보여주고 설명 완료로 처리하지 않는다.

## 2. 실제 과제와 연습용 단서를 구분하기

사용자가 제시한 소개 예문은 다음과 같다.

> 이천캠퍼스에서 식단 운영을 담당하는 영양사 이하린입니다. 한 달의 식단을 어떻게 편성할지, 구성원들이 어떤 메뉴에 관심을 보이는지 살펴보려 합니다.

이 예문으로는 **영양사를 위한 메뉴 관심도 분석과 월간 식단 편성**을 예상할 수 있다. 실제 필수 기능·파일·기간·배점·운영 규칙이 확정된 것은 아니다. 주어진 과제 README와 실제 담당자의 답변부터 확인한다. 이전 셔틀 과제나 식사 복지 사진의 조건을 이번 과제에 자동으로 옮기지 않는다.

식단 과제에서 특히 확인할 내용:

- 편성 단위: 날짜·식당·식사 구분·배식 코너 중 어디까지 구분하는가?
- 관심의 의미: 조회·클릭·좋아요·설문·실제 식사 이용 중 무엇을 측정한 데이터인가?
- 관심도·만족도·실제 수요는 같은 지표가 아니다. 제공 횟수나 노출 수가 다르면 단순 반응 합계도 비교 기준을 확인한다.
- 영양·예산·메뉴 반복·조리 가능 여부·특식 일정은 담당자에게 확인한다. 숫자나 정책을 만들어 넣지 않는다.
- 월간 식단 편집이 필요한지, 분석과 추천만 필요한지 구분한다. 식수 예측·잔반 최적화는 관련 요구와 데이터가 있을 때 추가한다.

처음 보낼 DM 초안은 가장 중요한 2~3개 질문으로 줄인다. 예:

> 현재 식단 편성과 구성원 관심도 확인 중 가장 어려운 업무는 무엇인가요? 최종적으로 직접 편집할 월간 식단표와 분석 자료 중 어떤 결과가 필요한가요? 제공 데이터에서 관심도를 나타내는 항목과 반드시 지켜야 하는 편성 규칙도 알려주세요.

읽을 수 있는 파일에서 알 수 있는 사실을 담당자에게 다시 묻지 않는다. 질문으로만 시간을 소모하지 말고, 답이 구현을 바꾸는 조건을 우선한다.

## 3. 과제 환경에 가져오기

공개 자료 반입이 허용된 환경에서만 아래 방식을 사용한다. `/tmp/261031`이 이미 있으면 삭제하지 말고 출처와 내용을 먼저 확인한다.

```sh
# 실제 과제 프로젝트에서 실행한다.
git clone https://github.com/Ea3124/261031.git /tmp/261031
bash /tmp/261031/setup.sh "$PWD"
```

`setup.sh`는 지정한 기존 프로젝트에 이 안내서와 아래 스킬 7개를 생성하고, `RULE.md`가 없으면 동봉된 지침도 복사한다. 기존 `RULE.md`는 내용이 달라도 보존한다. 인자를 생략하면 현재 디렉터리를 사용한다. 키트 자체나 그 하위 폴더에는 설치하지 않는다. Python 3.8 이상이 필요하다.

```text
과제 프로젝트/
  readme.kit.md
  RULE.md
  .agents/skills/
    cofa-workflow/SKILL.md
    cofa-discovery/SKILL.md
    cofa-prd/SKILL.md
    cofa-architecture/SKILL.md
    cofa-build/SKILL.md
    cofa-verify/SKILL.md
    cofa-understanding-coach/SKILL.md
```

기존 안내서와 스킬은 동일하면 보존하며, 내용이 다르면 덮어쓰기 전에 중지한다. 기존 `RULE.md`는 실제 과제 규칙을 보호하기 위해 내용과 관계없이 보존한다. 과제 README·코드·데이터·AGENTS.md·Git 설정·훅을 바꾸지 않는다. 패키지 설치, 앱 실행, 앱 검증, 커밋, 외부 전송도 설치 단계에 포함하지 않는다. 설치 도중 디스크나 권한 오류가 나면 일부 파일이 생성될 수 있으므로 원인을 해결하고 재실행한다.

설치 후 과제 환경의 Codex에 다음처럼 요청한다.

```text
$cofa-workflow
실제 과제 안내와 README, 제공 데이터, 기존 코드를 먼저 확인해 줘.
담당자 문답 → PRD → 최소 설계 → 구현 → 검증 흐름으로 진행하고,
핵심 단계마다 작은 검증과 내 이해를 확인하는 역질문 한 개를 반복해 줘.
필수 조건을 바꾸는 미확인 사항은 먼저 질문하고,
답변과 무관한 작업은 계속 진행해 줘.
```

설치기를 쓸 수 없다면 다음 요청으로 이 문서에서 직접 스킬을 생성한다.

```text
readme.kit.md를 읽고 "skill:" 표식이 붙은 코드 블록 7개를
각각 .agents/skills/<스킬 이름>/SKILL.md로 생성해 줘.
각 블록의 YAML 머리말과 본문을 그대로 사용하고,
다른 내용의 기존 파일은 덮어쓰지 말고 차이를 알려줘.
생성된 파일의 name·description·경로와 단계별 연결을 확인해 줘.
아직 과제 기능을 임의로 구현하거나 새 도구를 설치하지 마.
```

스킬 하나는 `name`과 `description`을 포함한 `SKILL.md`로 구성한다. 생성된 스킬은 관련 단계에 필요한 것만 읽는다. 형식과 프로젝트 경로는 [OpenAI 공식 스킬 문서](https://learn.chatgpt.com/docs/build-skills)를 참고했다. 이 문서는 `skill-creator`의 역할 범위·명확한 입출력·짧은 지침 원칙으로 새로 작성했다.

## 4. 과제 진행 중 공유할 최소 기록

과제에 동등한 문서가 있으면 재사용하고, 필수 제출 파일명은 실제 안내를 따른다. 별도 형식이 없을 때 아래 세 파일을 작업 프로젝트에 만든다. 설치기가 빈 문서를 미리 만들지는 않는다.

| 기록 | 담을 내용 |
| --- | --- |
| `PRD.md` | 목표·사용자·필수 기능·운영 제약·우선순위·요구별 완료 조건·남은 질문 |
| `WORKLOG.md` | 데이터 의미와 출처·DM 답변·입출력 계약·설계 선택·관련 코드·검증 결과·현재 상태·다음 작업 |
| `EXPLAIN.md` | 실제 처리 흐름·선택 이유·한계·단계별 역질문·사용자 답변 요지·점검 상태 |

기록에는 확인된 사실, 임시 가정, 미확인 사항을 구분한다. 질문 초안 작성·실제 전송·실제 답변 수신도 구분한다. 명령 실행 성공, 기능 검증 성공, 사용자 이해 확인은 서로 다른 상태다. 같은 내용을 여러 문서에 복제하지 말고 근거 위치를 연결한다.

요구와 구현은 다음 연결로 추적한다.

> 요구 식별자 → 문서 또는 담당자 답변의 근거 → 입력과 기대 결과 → 구현 파일·함수 → 실제 검증 결과

설계와 구현을 바꿀 때는 다음만 짧게 남긴다.

> 발견한 근거 → 바꾼 판단과 이유 → 영향 범위 → 같은 조건의 재검증 결과

# 전체 작업 흐름

## 입력과 결과

입력은 실제 과제 안내, README, 제공 데이터, 기존 코드와 현재 작업 상태다. 결과는 실제로 작동하고 검증된 필수 사용자 흐름, 관련 기록, 사용자가 직접 설명한 범위와 남은 한계다.

## 시작과 재개

1. 과제 안내·README·적용되는 AGENTS.md와 RULE.md, 현재 파일·Git 상태를 확인한다. 모델·도구·자료 반입·DM·화면 확인·제출·AI 지원 종료 시점은 실제 안내를 따른다. 이 스킬은 별도 권한을 만들지 않는다.
2. 기존 PRD.md·WORKLOG.md·EXPLAIN.md 또는 동등 기록을 읽고 실제 구현과 대조한다. 새로운 앱이나 문서를 무조건 만들지 않는다.
3. 목표, 필수 조건, 현재 단계, 미결 질문과 다음 작업을 짧게 정한다. 시간 제한이 실제로 확인되면 구현·검증·설명·제출에 필요한 시간을 배분한다. 180분을 고정 조건으로 삼지 않는다.

## 단계 연결

- 처음에는 ../cofa-discovery/SKILL.md로 데이터 의미와 담당자 답변을 확인한다.
- 핵심 목표가 확인되면 ../cofa-prd/SKILL.md로 최소 요구와 완료 조건을 만든다.
- ../cofa-architecture/SKILL.md로 필수 흐름의 입출력·계산·저장·화면 경로를 정한다.
- ../cofa-build/SKILL.md로 실제 데이터에서 화면까지 작은 흐름을 완성한다.
- ../cofa-verify/SKILL.md로 각 단계와 구현 결과를 확인하고 실패 원인을 고친다.
- 담당자 문답과 데이터 해석, PRD, 설계, 핵심 계산, 전체 사용자 흐름, 최종 검증이 각각 정리될 때 ../cofa-understanding-coach/SKILL.md로 짧은 역질문 한 개를 제시한다. 사소한 편집마다 묻지 않는다.

각 핵심 단계의 기본 반복은 작은 검증 → 근거와 현재 상태 기록 → 역질문 한 개 → 사용자 답변에 따른 보완이다. 검증은 짧게 하되 결과를 좌우하는 부분을 확인한다. 질문 답변을 기다리는 동안 확정된 조건의 독립 작업은 계속한다. 정답을 먼저 공개하거나 사용자 답변 없이 이해 완료로 처리하지 않는다. 역질문은 일상적인 구현 승인 요청이 아니다.

## 되돌아갈 기준

- 목표·업무 규칙·데이터 의미가 바뀌면 문답과 PRD로 돌아가 영향받는 설계·코드·검사를 함께 수정한다.
- 단순 구현 오류면 해당 부분을 수정하고 같은 사례로 재검증한다.
- 읽은 문서와 담당자 답변이 충돌하면 결과를 바꾸는 쟁점을 재질문한다. 대기 중에는 독립 작업을 수행한다.
- 설명의 빈틈만 있으면 짧은 해설과 재질문으로 보완한다. 제품 기능을 불필요하게 추가하지 않는다.

## 완료

필수 요구의 검증 결과, 실제 실행 방법, 미해결·미검증 항목, 이해 점검 상태를 보고한다. 다음 단계가 금지되거나 AI 지원이 종료되는 시점에는 실제 안내를 따른다. 설치 성공·빌드 성공·남은 시간 종료만으로 앱 검증이나 이해 점검 완료를 선언하지 않는다.

# 과제·데이터와 담당자 문답

## 입력과 결과

입력은 과제 지문, README, 실제 데이터 파일과 담당자 소개·답변이다. 결과는 주 사용자·해결할 결정·데이터 의미·확인된 조건·근거·미결 질문이며 WORKLOG.md 또는 동등 기록에 남긴다.

## 먼저 조사하기

1. 제공 파일 목록과 표본을 읽고 행의 단위, 식별자, 파일 연결 관계, 날짜·시간·수량 단위를 확인한다.
2. 필요한 범위의 결측·중복·잘못된 값·조인에 따른 행 증가를 확인한다. 원본 데이터를 보존한다.
3. 자료로 확인된 내용과 담당자에게 물어야 할 해석을 나눈다. 샘플 파일명이나 예상 시나리오를 실제 제공 자료로 취급하지 않는다.

## 담당자에게 물을 내용

- 주 사용자가 어떤 결정을 하며 현재 무엇이 가장 어려운가?
- 반드시 필요한 결과와 선택 가능한 기능은 무엇인가?
- 성공 기준, 강제 제약, 선호 조건과 충돌 시 우선순위는 무엇인가?
- 지표·날짜·결측·경계값은 어떤 의미인가? 추가 규칙이나 파일이 있는가?
- 정상 사례와 허용할 수 없는 결과는 무엇인가?

초안은 한 번에 중요한 2~3개 질문으로 줄인다. 답변에 따라 구현·기대값이 어떻게 달라지는지 짧게 덧붙인다. 이미 확인한 내용을 반복해서 묻지 않는다. DM 전송은 실제 환경이 허용하는 담당자 채널과 조작 방식만 따른다. 직접 전송할 수 없으면 사용자에게 초안을 제공한다. 실제 전송·답변 수신을 확인하기 전에는 각각 미확인으로 기록한다.

답변이 오면 확인된 범위만 반영하고, 중요한 해석은 작은 입력·기대 결과로 재확인한다. 답변이 없는 조건을 확정하지 않으며 그 조건과 무관한 조사·환경 점검은 계속한다.

식단 과제라면 편성 단위와 관심도 지표를 먼저 확인한다. 조회·선호·만족·이용량을 섞지 않는다. 노출·제공 횟수, 품절과 결측의 의미가 해석을 바꾸는지 살핀다. 예산·영양·반복 제한·특식 정책의 숫자를 임의로 정하지 않는다.

## 단계 완료와 점검

목표와 필수 조건이 PRD로 옮겨질 정도로 확인되면 구현 준비로 진행한다. 남은 질문의 영향과 다음 행동을 기록한다. 대표 데이터 한 건과 담당자 답변이 모순되지 않는지 확인한 뒤 이해 점검 스킬로 사용자가 핵심 업무를 자기 말로 설명하게 한다.

# 최소 PRD

## 입력과 결과

입력은 과제 명시 사항, 확인된 담당자 답변, 데이터 의미와 미결 질문이다. 결과는 PRD.md 또는 기존 동등 문서의 짧고 검증 가능한 요구사항이다. 내용을 길게 꾸미는 대신 구현과 확인에 필요한 판단을 남긴다.

## 작성할 내용

1. 사용자와 해결할 업무, 현재 문제, 기대 결과를 한 문단으로 적는다.
2. 필수 기능과 여유가 있을 때 할 기능을 나눈다. 과제에 없는 자동 편성·예측·인증·외부 연동을 추가하지 않는다.
3. 반드시 지켜야 할 조건과 순위를 정하는 선호 기준을 구분하고, 근거와 우선순위를 적는다.
4. 요구마다 R1 같은 식별자를 붙이고 출처, 사용자 입력·동작, 기대 결과, 오류·데이터 부족 시 동작, 확인 방법을 적는다.
5. 결과에 영향을 주는 미확인 항목을 남긴다. 담당자가 확정해야 할 조건을 임시 숫자로 채우지 않는다.

예를 들어 식단표를 직접 편집해야 한다는 요구가 확인되면 날짜·식당·식사 구분을 선택하고 메뉴를 변경했을 때 화면과 저장 결과가 어떻게 바뀌어야 하는지 적는다. 저장·반복 제한이 요구되지 않았다면 예시만으로 필수 기능에 넣지 않는다.

# 최소 아키텍처

## 입력과 결과

입력은 확인된 PRD, 실제 파일 구조, 데이터와 실행 환경이다. 결과는 WORKLOG.md 또는 기존 설계 기록에 남긴 처리 경로, 입출력 계약, 주요 파일의 책임과 선택 이유다.

## 설계 판단

- 기존 앱과 의존성을 먼저 확인하고 재사용한다. 언어·프레임워크·데이터베이스·호스팅을 미리 고정하지 않는다.
- 데이터 읽기 → 정규화·검증 → 업무 계산 → 필요한 저장 → 화면 표시의 경로를 그린다. 저장이 필요하지 않은 기능에 서버나 데이터베이스를 추가하지 않는다.
- 사용자 입력, 식별자·단위·시간 기준, 함수나 API의 출력, 오류·결과 없음 상태를 정한다.
- 핵심 계산은 화면 코드와 구분해 작은 사례로 검증할 수 있게 한다. 별도 서버가 없어도 된다.
- 강제 제약을 통과한 후보에 선호 기준을 적용한다. 단순한 기준안을 먼저 만들고 복잡한 최적화나 모델은 실제 필요와 시간에 맞춰 선택한다.
- 언어 모델을 새로 연결해야 한다고 가정하지 않는다. 집계·비교·조건 검사는 가능한 범위에서 재현 가능한 코드로 처리한다.

각 경계에는 실제 입력과 기대 출력 하나를 붙여 단위·날짜·필드의 해석이 맞는지 확인한다. 선택한 구조의 이유와 구현에 영향을 줄 한계를 기록하되 큰 설계 문서로 확장하지 않는다.

## 단계 완료와 점검

## 작은 단위로 완성하기

1. 실행 방법과 기존 동작을 확인하고, 실제 입력 한 건에 대한 단순한 기준 계산을 만든다.

5. 핵심 흐름이 동작한 뒤 필수 조건과 사용성을 다듬는다. 장식이나 부가 기능 때문에 필수 흐름을 미완성으로 두지 않는다.

관련 코드·실행 명령·바뀐 판단을 WORKLOG.md 또는 기존 기록에 연결한다. 미리보기가 열리는 주소·포트·접근 방식은 실제 환경의 안내와 실행 출력으로 확인한다. 도구가 없거나 조작이 허용되지 않으면 수동 확인을 요청하고 미검증 상태를 남긴다.

# 검증과 수정

## 입력과 결과

입력은 PRD의 완료 조건, 실제 데이터·코드, 실행 환경과 이전 검증 기록이다. 결과는 입력·기대값·실제값·실행 근거가 연결된 통과·실패·미검증 상태다.

## 단계에 맞게 확인하기

- 문답·데이터 단계: 행의 단위·조인·기간·지표가 실제 표본과 맞는지 확인한다.
- PRD 단계: 필수 요구와 완료 조건이 모순되지 않고 실제 입력으로 확인 가능한지 점검한다.
- 설계 단계: 입력·출력·단위·오류 상태와 작은 기대 사례가 이어지는지 확인한다.
- 계산 단계: 손계산·별도 간단한 계산·담당자가 확인한 사례로 기대값을 먼저 정하고 구현 결과와 비교한다. 구현 함수의 출력을 기대값으로 복사하지 않는다.
- 화면 단계: 실제 데이터로 대표 사용자 입력부터 결과 표시까지 확인한다. 저장·내보내기 등이 필수라면 그 결과도 다시 읽어 확인한다.

정상 사례, 실제 업무와 관련 있는 경계 조건, 불가·결과 없음·데이터 부족 사례를 선택한다. 기능을 그대로 복제하는 테스트나 무조건 성공하는 검사를 만들지 않는다. 검사가 핵심 오류를 잡는지 의심되면 작은 반례를 추가하거나 격리된 복사본에서 알려진 결함을 탐지하는지 확인한다. 모든 변경에 결함 주입을 강제하지 않는다.

개선 비교는 같은 입력·기간·조건으로 한다. 예측 과제는 과거 정보로 이후 시점을 검증하고 미래 정보를 섞지 않는다. 품절 시 제공량을 곧바로 전체 수요로 보지 않는다. 추정·모의 값과 실측을 구분하고, 증명하지 않은 전역 최적이나 측정하지 않은 개선율을 주장하지 않는다.

## 기록과 실패 처리

WORKLOG.md 또는 동등 기록에 요구 식별자, 입력·기대·실제, 명령 또는 조작, 실행 대상, 상태와 남은 한계를 적는다. 관련 변경 후에는 영향받는 검증을 다시 실행한다. 실패하면 원인을 고치고 같은 사례로 재검증한다. 기대값을 근거 없이 낮추거나 실패 검사를 없애 통과시키지 않는다.

실제 화면을 확인하지 못했으면 화면 미검증이라고 기록한다. 정적 코드 확인·빌드·계산 테스트·화면 확인을 구분한다. 필수 요구와 관련 검증이 통과하면 새로운 근거 없이 검사를 반복하지 않는다.

# 짧은 이해 점검

## 입력과 결과

입력은 방금 완료한 단계, 실제 과제·데이터·구현·검증 근거와 이전 사용자 답변이다. 결과는 사용자가 직접 설명한 내용과 설명 가능·보완 필요·확인 불가·응답 대기 상태다.

## 한 번의 점검

1. 현재 단계의 중요한 판단 하나를 고르고 답을 확인할 문서·컬럼·코드·실행 근거를 확보한다. 아직 구현하지 않은 구조를 사실로 전제하지 않는다.
2. 실제 과제에 맞는 질문 한 개를 먼저 제시한다. 사용자가 질문 목록을 원하지 않는 한 여러 문제를 한꺼번에 내지 않는다. 답변 전에 모범답안이나 답이 그대로 드러나는 해설을 함께 제시하지 않는다.
3. 사용자 답변을 기다린다. 질문과 무관한 확정된 구현·검증은 계속할 수 있다. 사용자의 업무 결정이 필요한 부분은 답을 받기 전 확정하지 않는다.
4. 답변을 실제 근거와 대조해 맞는 부분 → 보완할 부분 → 확인 근거 순으로 짧게 피드백한다. 내용이 맞으면 전문 용어나 표현을 불필요하게 문제 삼지 않는다.
5. 핵심 오해가 있으면 작은 실제 사례로 설명하고 자기 말로 다시 설명할 후속 질문 한 개를 한다. 해설 직후 따라 말한 것과 이후 독립적으로 설명한 것을 구분한다.

질문 예시는 현재 결과에 맞게 바꾼다.

- 문답·데이터 뒤: 주 사용자가 해결하려는 결정은 무엇이며 관심도 컬럼은 무엇을 측정하는가?
- PRD 뒤: 요구 하나가 충족됐다고 판단할 입력과 기대 결과는 무엇인가?
- 설계 뒤: 입력을 바꾸면 어떤 데이터·함수·화면이 영향을 받는가?
- 핵심 계산 뒤: 실제 데이터 한 건에 규칙을 적용하면 결과가 어떻게 나오는가?
- 전체 흐름 뒤: 메뉴나 필터 변경이 화면과 필요한 저장 결과에 어떻게 반영되는가?
- 검증 뒤: 정확성을 뒷받침한 사례는 무엇이고 어떤 조건은 아직 확인하지 못했는가?

한 번의 점검은 질문 하나와 짧은 피드백으로 마친다. 답이 충분하면 다음 단계로 진행한다. 사용자 응답이 없으면 응답 대기로 남기고, 설명 자료를 제공한 것만으로 이해했다고 표시하지 않는다. 나중에 점검하자는 요청은 보류로 기록한다.

## 기록과 경계

EXPLAIN.md 또는 동등 기록에 단계·질문·사용자 답변 요지·점검 상태·근거·보완할 내용을 간결하게 남긴다. 코드는 고치지 않는다. 답변 중 기능 변경이 요청되면 그 요청을 요구·구현 단계에 전달한다.

자료에 접근할 수 없으면 확인 불가로 남기고 일반 연습 질문임을 밝힌다. 공식 문제·배점·합격 여부를 예측하지 않는다. 실제 후속 서술형 등 AI 지원이 종료되는 시점 이후에는 연습을 계속하거나 답변을 대신 만들지 않는다. 정확한 종료 경계는 해당 과제 안내로 확인한다.

## 6. 시작·재개·마무리 때 확인할 것

- 시작: 실제 안내와 데이터 → 가장 큰 미확인 조건 → 첫 번째 작동 흐름을 정한다.
- 진행: 한 번에 필요한 스킬을 읽고, 핵심 단계마다 작은 검증과 역질문을 반복한다.
- 변경: 새로운 답변이나 실패 근거가 나온 부분의 요구·설계·코드·검사를 함께 바꾼다.
- 재개: 요약만 믿지 말고 실제 파일·실행 상태·미결 질문·응답 대기 항목을 확인한다.
- 마무리: 실행 방법, 충족한 요구, 실제 검증 결과, 남은 한계와 이해 점검 상태를 정리한다. 실제 제출 절차와 AI 지원 종료 시점은 과제 안내를 따른다.
