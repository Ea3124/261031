# COFA 과제 작업 키트

과제 환경에서 이 문서 하나를 읽고 `AGENTS.md`와 필요한 스킬을 만들거나, 함께 제공된 `setup.sh`로 생성한다. 저장소에는 `readme.kit.md`, `setup.sh`, `RULE.md` 세 파일만 둔다. 생성한 `AGENTS.md`·스킬과 실제 과제의 코드·데이터·README·작업 기록은 과제 프로젝트에 둔다.

동봉된 `RULE.md`는 이전에 정리한 실전 운영 지침을 복원한 것이다. 시작할 때 읽되, 이번 과제의 실제 안내와 기존 프로젝트 규칙을 우선한다.

## 1. 우리가 합의한 작업 흐름

**과제·데이터 확인 및 담당자 문답 → 간결한 PRD → 최소 아키텍처 → 핵심 흐름 구현 → 최종 검증과 정리**로 진행한다. 각 핵심 단계 직후 **설계 검증 → 단계에 맞는 로직·동작 검증 → 근거 기록 → 사용자에게 역질문 한 개 → 답변에 따른 보완**을 반복한다. 마지막에 몰아서 검증하거나 이해를 확인하지 않는다.

설계 검증은 목표·요구·데이터·구조가 서로 맞는지, 고려하지 못한 조건이나 모순이 있는지 살피는 일이다. 로직·동작 검증은 규칙과 처리 결과가 맞는지 확인하는 일이다. PRD 단계에서는 누락·충돌·정상 및 비정상 시나리오를 검토하고, 코드가 생기면 계산 테스트·연결 테스트·실제 사용자 흐름 확인 등 필요한 검사를 실행한다. 아직 구현하지 않은 기능을 테스트했다고 기록하지 않는다.

| 단계 | 설계 검증 | 로직·동작 검증 | 역질문의 초점 |
| --- | --- | --- | --- |
| 과제·데이터 확인 및 DM | 사용자의 결정과 데이터가 연결되는지, 숨은 가정은 없는지 | 실제 행·컬럼·조인·단위·경계값이 해석과 맞는지 | 어떤 데이터를 근거로 왜 이 문제를 풀기로 했는가? |
| PRD | 놓친 요구·제약·사용자 상황·목표 충돌은 없는지 | 구체적인 입력에서 정상·비정상 기대 결과를 정할 수 있는지 | 이 완료 조건이 필요한 이유와 빠뜨릴 수 있는 상황은 무엇인가? |
| 아키텍처 | 역할·경계·저장 방식·실행 환경이 요구에 맞는지 | 데이터부터 화면까지 입출력과 실패 시 처리가 이어지는지 | 왜 이 구조이며 각 경계에서 실패하면 어떻게 되는가? |
| 핵심 계산과 화면 구현 | 실제 코드가 합의한 설계와 조건을 지키는지 | 독립 기대값·기능 테스트·정상 및 비정상 사용자 흐름 | CSV가 어떤 변환을 거쳐 화면의 결과와 수치가 되는가? |
| 최종 검증과 수정 | 남은 한계·조건 변경·개선 대안을 설명할 수 있는지 | 관련 데이터·인프라 예외와 같은 조건의 재검증 | 어떤 원자료로 독립 검증했으며 다음 개선을 어떻게 확인할 것인가? |

역질문은 아키텍처를 의식적으로 설명하고, 데이터에 근거한 의사결정의 이유·작동 방식·정상과 예외 동작·수치의 검증 근거·개선 방법을 자기 말로 설명하는 연습이다. 현재 단계와 실제 구현에 맞는 주제 하나씩 고른다. 매번 모든 영역을 한꺼번에 질문하거나 고정된 검사 목록을 모두 수행하지 않는다.

문답은 처음 한 번으로 끝나지 않는다. 구현이나 검증에서 새로운 업무 조건이 발견되면 담당자에게 다시 묻고 PRD·설계·검사를 함께 갱신한다. 작은 구현 오류는 해당 부분만 수정하고 재검증한다.

역질문은 사용자의 이해 점검이다. 매번 다음 작업의 승인을 받는 절차가 아니다. 답변을 기다리는 동안 확정된 조건에 관한 독립 작업은 계속할 수 있다. 사용자 답변 없이 이해했다고 기록하거나, 정답을 먼저 보여주고 설명 완료로 처리하지 않는다.

## 2. 실제 과제를 기준으로 시작하기

실제 필수 기능·파일·기간·운영 규칙은 과제 README와 담당자 답변으로 확인한다. 특정 인물·장소·예상 시나리오를 출발점으로 고정하지 않는다. 과거 과제의 조건을 새 과제에 자동으로 옮기지 않는다.

먼저 확인할 내용:

- 사용자가 내려야 할 결정과 필요한 결과물은 무엇인가?
- 데이터 한 행은 무엇을 뜻하며 어떤 단위·기간·모집단을 다루는가?
- 지표는 무엇을 측정하고, 관측값으로 무엇까지 판단할 수 있는가?
- 결측·중복·조인 실패·분모 0·경계값이 결과에 어떤 영향을 주는가?
- 반드시 지킬 조건과 조정 가능한 선호는 무엇이며 충돌 시 무엇이 우선인가?
- 결과의 수정·저장·내보내기 등은 실제로 필요한가?

처음 보낼 DM 초안은 가장 중요한 2~3개 질문으로 줄인다. 예:

> 현재 어떤 결정을 내릴 때 가장 어려움을 겪고 계신가요? 최종적으로 어떤 결과를 확인하거나 수정할 수 있어야 하나요? 제공 데이터의 주요 지표와 반드시 지켜야 할 업무 규칙도 알려주세요.

읽을 수 있는 파일에서 알 수 있는 사실을 담당자에게 다시 묻지 않는다. 질문으로만 시간을 소모하지 말고, 답이 구현을 바꾸는 조건을 우선한다.

## 3. 과제 환경에 가져오기

공개 자료 반입이 허용된 환경에서만 아래 방식을 사용한다. `/tmp/261031`이 이미 있으면 삭제하지 말고 출처와 내용을 먼저 확인한다.

```sh
# 실제 과제 프로젝트에서 실행한다.
git clone https://github.com/Ea3124/261031.git /tmp/261031
bash /tmp/261031/setup.sh "$PWD"
```

`setup.sh`는 지정한 기존 프로젝트에 이 안내서와 아래 스킬 8개를 생성하고, `AGENTS.md`가 없으면 이 문서의 원문에서 생성한다. `RULE.md`가 없으면 동봉된 지침도 복사한다. 기존 `AGENTS.md`와 `RULE.md`는 내용이 달라도 보존한다. 인자를 생략하면 현재 디렉터리를 사용한다. 키트 자체나 그 하위 폴더에는 설치하지 않는다. Python 3.8 이상이 필요하다.

```text
과제 프로젝트/
  readme.kit.md
  AGENTS.md
  RULE.md
  .agents/skills/
    cofa-workflow/SKILL.md
    cofa-discovery/SKILL.md
    cofa-prd/SKILL.md
    cofa-architecture/SKILL.md
    cofa-build/SKILL.md
    cofa-verify/SKILL.md
    cofa-understanding-coach/SKILL.md
    cofa-handoff/SKILL.md
```

기존 안내서와 스킬은 동일하면 보존하며, 내용이 다르면 덮어쓰기 전에 중지한다. 기존 `AGENTS.md`와 `RULE.md`는 실제 과제 규칙을 보호하기 위해 내용과 관계없이 보존하며, 보존한 경로를 출력한다. 과제 README·코드·데이터·Git 설정·훅을 바꾸지 않는다. 패키지 설치, 앱 실행, 앱 검증, 커밋, 외부 전송도 설치 단계에 포함하지 않는다. 설치 도중 디스크나 권한 오류가 나면 일부 파일이 생성될 수 있으므로 원인을 해결하고 재실행한다.

설치 후 과제 환경의 Codex에 다음처럼 요청한다.

```text
$cofa-workflow
실제 과제 안내와 README, AGENTS.md, RULE.md, 제공 데이터, 기존 코드를 먼저 확인해 줘.
담당자 문답 → PRD → 최소 설계 → 구현 → 검증 흐름으로 진행하고,
핵심 단계마다 설계 검증과 로직·동작 검증을 반복해 줘.
PRD에서는 놓친 요구·가정·예외·충돌을 검토하고,
웹 구현에서는 정상·비정상 동작과 데이터·인프라 경계 조건을 실제로 테스트해 줘.
역질문은 한 번에 한 개씩, 내가 우리의 아키텍처와 판단 근거를
의식적으로 설명할 수 있도록 현재 단계에 맞춰 골라 줘.
CSV의 어떤 데이터가 어떤 변환·계산·전달·저장을 거쳐 웹 화면이 되는지,
왜 그 방법을 선택했고 정상·비정상 및 데이터·인프라 예외에서 어떻게 작동하는지,
구체적인 수치는 어떤 원자료와 별도 계산으로 독립 검증했는지,
추가 개선 방법과 그 효과를 확인할 방법까지 생각하게 해 줘.
필수 조건을 바꾸는 미확인 사항은 먼저 질문하고,
답변과 무관한 작업은 계속 진행해 줘.
```

설치기를 쓸 수 없다면 다음 요청으로 이 문서에서 직접 지침과 스킬을 생성한다.

```text
readme.kit.md를 읽고 "skill:" 표식이 붙은 코드 블록 8개를
각각 .agents/skills/<스킬 이름>/SKILL.md로 생성해 줘.
"artifact: AGENTS.md" 표식의 코드 블록은 과제 루트의 AGENTS.md로 생성해 줘.
기존 AGENTS.md가 있으면 내용과 관계없이 보존하고 그 사실을 알려줘.
스킬 블록의 YAML 머리말과 본문, AGENTS.md 블록의 본문을 그대로 사용해 줘.
다른 내용의 기존 안내서·스킬은 덮어쓰지 말고 차이를 알려줘.
스킬의 name·description·경로·단계별 연결과 AGENTS.md의 참조 경로를 확인해 줘.
아직 과제 기능을 임의로 구현하거나 새 도구를 설치하지 마.
```

스킬 하나는 `name`과 `description`을 포함한 `SKILL.md`로 구성한다. 생성된 스킬은 관련 단계에 필요한 것만 읽는다. 생성에 필요한 형식과 각 스킬의 지침은 이 문서의 코드 블록에 모두 들어 있다.

### AGENTS.md 원문

아래 블록은 스킬이 아니라 과제 루트에 생성할 공통 진입 지침이다. 상세 절차는 함께 생성되는 해당 스킬에서 읽는다.

<!-- artifact: AGENTS.md -->
```markdown
# 과제 작업 지침

## 시작과 재개

- 실제 과제 안내·README·RULE.md를 먼저 읽고 목표·필수 조건·제출 방식을 확인한다. 특정 도메인·기술 스택·시간 제한을 미리 가정하지 않는다.
- 현재 코드·제공 데이터·작업 경로·Git 상태를 확인한다. 기존 PRD.md·WORKLOG.md·EXPLAIN.md·handoff.md 또는 동등 기록이 있으면 실제 파일·실행 상태와 대조한다. 없는 기록을 확인했다고 표현하지 않는다.

## 필요한 스킬 선택

- 전체 진행은 .agents/skills/cofa-workflow/SKILL.md에서 시작하고, 현재 단계에 필요한 로컬 스킬만 읽는다.
- 검증 실패·반복 오류는 .agents/skills/cofa-verify/SKILL.md, 이해 점검은 .agents/skills/cofa-understanding-coach/SKILL.md를 사용한다.
- 세션 전환·중단·맥락 부족·완료와 인계 후 재개에는 .agents/skills/cofa-handoff/SKILL.md를 사용한다.

## 공통 작업 원칙

- 확인된 요구·임시 가정·미확인 사항을 구분한다. 결과를 바꾸는 미확인 조건은 질문하고, 그 답과 무관한 확정된 작업은 계속한다. 불필요한 구현 승인 대기를 반복하지 않는다.
- 필수 기능·제외 범위·기존 기능과 데이터에 미치는 영향을 정하고, 필요한 만큼만 설계·구현한다. 새로운 업무 조건이 확인되면 요구·설계·검사를 함께 갱신한다.
- 핵심 단계마다 설계의 누락·모순을 검토하고 단계에 맞는 로직·정상 및 예외 동작을 검증한다. 수치는 원자료와 별도 계산으로 확인하며 실제 실행 근거를 남긴다.
- 역질문은 현재 단계의 중요한 판단 하나를 고른다. 아키텍처·CSV부터 화면까지의 흐름·선택 이유·예외 동작·검증 근거·개선 방법을 자기 말로 설명하게 한다. 정답을 먼저 공개하거나 사용자 답변 없이 이해 완료로 처리하지 않는다.
- 실패는 같은 조건으로 재현하고 처음 잘못되는 지점을 찾아 수정·회귀 검증한다. 기대값 완화·예외 무시·근거 없는 재시도로 통과를 만들지 않는다.
- 중요한 결정·검증·미결 질문을 기존 기록에 갱신하고, 인계 때는 실제 상태·근거·다음 작업을 남긴다. 완료 보고에서 통과·실패·미검증과 이해 점검 상태를 구분한다.
```

## 4. 과제 진행 중 공유할 최소 기록

과제에 동등한 문서가 있으면 재사용하고, 필수 제출 파일명은 실제 안내를 따른다. 별도 형식이 없으면 아래 기록을 작업 프로젝트에 작성한다. `handoff.md`는 세션 전환·중단·완료 등 인계가 필요한 때만 작성한다. 설치기가 빈 문서를 미리 만들지는 않는다.

| 기록 | 담을 내용 |
| --- | --- |
| `PRD.md` | 목표·사용자·필수 기능·운영 제약·우선순위·요구별 완료 조건·남은 질문 |
| `WORKLOG.md` | 데이터 의미와 출처·DM 답변·입출력 계약·설계 선택·관련 코드·설계 및 로직 검증·독립 기대값의 근거·현재 상태·다음 작업 |
| `EXPLAIN.md` | CSV부터 화면까지의 실제 흐름·의사결정 이유·정상 및 예외 동작·수치의 독립 검증 근거·개선 대안·단계별 역질문과 사용자 답변·점검 상태 |

기록에는 확인된 사실, 임시 가정, 미확인 사항을 구분한다. 질문 초안 작성·실제 전송·실제 답변 수신도 구분한다. 명령 실행 성공, 기능 검증 성공, 사용자 이해 확인은 서로 다른 상태다. 같은 내용을 여러 문서에 복제하지 말고 근거 위치를 연결한다.

> 요구 식별자 → 문서 또는 담당자 답변의 근거 → 입력과 기대 결과 → 구현 파일·함수 → 실제 검증 결과

> 발견한 근거 → 바꾼 판단과 이유 → 영향 범위 → 같은 조건의 재검증 결과

```markdown
# 과제·데이터와 담당자 문답

## 입력과 결과

입력은 과제 지문, README, 실제 데이터 파일과 담당자 소개·답변이다. 결과는 주 사용자·해결할 결정·데이터 의미·확인된 조건·근거·미결 질문이며 WORKLOG.md 또는 동등 기록에 남긴다.

## 먼저 조사하기

1. 제공 파일 목록과 표본을 읽고 행의 단위, 식별자, 파일 연결 관계, 날짜·시간·수량 단위를 확인한다.
2. 필요한 범위의 결측·중복·잘못된 값·조인에 따른 행 증가를 확인한다. 원본 데이터를 보존한다.
3. 자료로 확인된 내용과 담당자에게 물어야 할 해석을 나눈다. 샘플 파일명이나 예상 시나리오를 실제 제공 자료로 취급하지 않는다.

## 담당자에게 물을 내용

- 주 사용자가 어떤 결정을 하며 현재 무엇이 가장 어려운가?
- 반드시 필요한 결과와 선택 가능한 기능은 무엇인가?
- 성공 기준, 강제 제약, 선호 조건과 충돌 시 우선순위는 무엇인가?
- 지표·날짜·결측·경계값은 어떤 의미인가? 추가 규칙이나 파일이 있는가?
- 정상 사례와 허용할 수 없는 결과는 무엇인가?

초안은 한 번에 중요한 2~3개 질문으로 줄인다. 답변에 따라 구현·기대값이 어떻게 달라지는지 짧게 덧붙인다. 이미 확인한 내용을 반복해서 묻지 않는다. DM 전송은 실제 환경이 허용하는 담당자 채널과 조작 방식만 따른다. 직접 전송할 수 없으면 사용자에게 초안을 제공한다. 실제 전송·답변 수신을 확인하기 전에는 각각 미확인으로 기록한다.

답변이 오면 확인된 범위만 반영하고, 중요한 해석은 작은 입력·기대 결과로 재확인한다. 답변이 없는 조건을 확정하지 않으며 그 조건과 무관한 조사·환경 점검은 계속한다.

관측한 지표와 그 지표로 판단하려는 대상을 구분한다. 노출·기간·모집단이 다른 값의 단순 비교가 타당한지 확인하고, 데이터에서 어떤 근거로 어떤 결정을 내리려는지 연결한다. 업무 정책이나 임계값을 임의로 정하지 않는다.
```

```markdown
# 최소 PRD

## 입력과 결과

입력은 과제 명시 사항, 확인된 담당자 답변, 데이터 의미와 미결 질문이다. 결과는 PRD.md 또는 기존 동등 문서의 짧고 검증 가능한 요구사항이다. 내용을 길게 꾸미는 대신 구현과 확인에 필요한 판단을 남긴다.

## 작성할 내용

1. 사용자와 해결할 업무, 현재 문제, 기대 결과를 한 문단으로 적는다.
2. 필수 기능과 여유가 있을 때 할 기능을 나누고, 이번 구현에서 제외할 범위를 명시한다. 기존 기능·공유 데이터 형식·사용자 흐름에 미치는 변경 영향도 짧게 적는다. 과제에 없는 자동화·예측·인증·외부 연동을 추가하지 않는다.
3. 반드시 지켜야 할 조건과 순위를 정하는 선호 기준을 구분하고, 근거와 우선순위를 적는다.
4. 요구마다 R1 같은 식별자를 붙이고 출처, 사용자 입력·동작, 기대 결과, 오류·데이터 부족 시 동작, 확인 방법을 적는다.
5. 결과에 영향을 주는 미확인 항목을 남긴다. 담당자가 확정해야 할 조건을 임시 숫자로 채우지 않는다.

결과의 직접 편집과 저장이 요구되면 어떤 입력을 바꿨을 때 화면과 저장 결과가 어떻게 달라져야 하는지 적는다. 요구되지 않은 저장이나 기능을 예시만으로 필수 범위에 넣지 않는다.

## 단계 완료와 점검

설계 검증으로 빠진 사용자 상황, 데이터에 없는 전제, 서로 충돌하는 제약·우선순위, 데이터 부족·저장 실패 때의 요구 누락을 실제 범위 안에서 살핀다. 발견한 사항은 요구에 추가하거나 미결 질문으로 남긴다.

로직 검증으로 핵심 요구 하나의 정상·비정상 입력과 기대 결과를 구체화하고 업무 규칙끼리 모순되지 않는지 확인한다. 코드가 없는 단계의 검토를 실행 테스트로 표현하지 않는다. 이해 점검 스킬로 완료 조건의 이유나 빠뜨리기 쉬운 사례 한 가지를 묻고 최소 설계로 넘긴다. 이후 요구가 바뀌면 영향받는 요구·설계·검사만 함께 갱신한다.
```

```markdown
## 설계 판단

- 기존 앱과 의존성을 먼저 확인하고 재사용한다. 언어·프레임워크·데이터베이스·호스팅을 미리 고정하지 않는다.
- CSV 읽기 → 형식·자료형·단위 정규화와 검증 → 필요한 조인·필터·집계 → 업무 판단·계산 → 필요한 API·상태·저장 → 화면 표시의 실제 경로를 그린다. 단계마다 입력·출력과 담당 파일·함수를 연결한다. 쓰지 않는 계층은 생략하고, 저장이 필요하지 않은 기능에 서버나 데이터베이스를 추가하지 않는다.
- 파일이나 엔터티의 식별자·연결 관계·일대다 관계를 정하고 조인으로 행이 늘어나는 영향을 확인한다. 실제 조회·수정·저장 흐름을 기준으로 필요한 자료형과 구조를 고른다.
- 원본 데이터·필터·파생 계산 결과·편집 상태의 관리 위치와 갱신 책임을 정한다. 입력을 바꿀 때 무엇을 다시 계산·조회·저장하는지, 기존 결과를 유지하거나 무효화하는 조건을 연결한다.
- 사용자 입력, 식별자·단위·시간 기준, 함수나 API의 출력, 오류·결과 없음 상태를 정한다.
- 핵심 계산은 화면 코드와 구분해 작은 사례로 검증할 수 있게 한다. 별도 서버가 없어도 된다.
- 강제 제약을 통과한 후보에 선호 기준을 적용한다. 단순한 기준안을 먼저 만들고 복잡한 최적화나 모델은 실제 필요와 시간에 맞춰 선택한다.
- 언어 모델을 새로 연결해야 한다고 가정하지 않는다. 집계·비교·조건 검사는 가능한 범위에서 재현 가능한 코드로 처리한다.

각 경계에는 실제 입력과 기대 출력 하나를 붙여 단위·날짜·필드의 해석이 맞는지 확인한다. 선택한 구조의 이유, 대안과의 차이, 조건이 바뀔 때의 영향과 한계를 기록하되 큰 설계 문서로 확장하지 않는다.

실제 구성에 맞는 데이터 예외와 인프라 예외를 골라 실패 전파를 검토한다. 빈 파일·잘못된 자료형·조인 누락·분모 0일 때 계산과 화면은 어떻게 되는가? 파일 읽기·서버 시작·API 요청·저장이 실패하면 어디서 감지하고 무엇을 표시하거나 보존하는가? 사용하는 구성 요소에만 적용하며, 아직 정하지 않은 동작은 구현 사실로 기록하지 않는다.
```

```markdown
# 검증과 근본 원인 디버깅

## 입력과 결과

입력은 현재 단계의 요구·설계, 실제 데이터·코드, 실행 환경과 이전 검증 기록이다. 결과는 설계 검토 결과와 입력·기대값·실제값·실행 근거가 연결된 로직·동작 검증 상태다. 설계 검토, 테스트 실행, 코드만 확인한 사항, 미검증 항목을 구분한다.

## 단계에 맞게 확인하기

- 문답·데이터 단계: 결정과 지표 사이에 빠진 가정을 검토하고 행의 단위·조인·기간·지표가 실제 표본과 맞는지 확인한다.
- PRD 단계: 놓친 사용자 상황·제약·데이터 부족·실패 처리·목표 충돌을 검토하고, 정상·비정상 입력과 기대 결과를 대조한다. 아직 없는 코드의 테스트를 통과했다고 기록하지 않는다.
- 설계 단계: CSV부터 화면까지 책임과 경계가 이어지는지, 데이터·인프라 실패를 어디서 처리하는지 검토하고 입출력·단위·오류 상태를 대표 사례로 확인한다.
- 계산 단계: 실제 CSV와 손계산·별도 계산 경로·담당자가 확인한 사례로 기대값을 먼저 정하고 구현 결과와 비교한다. 구현 함수의 출력을 기대값으로 복사하지 않는다.
- 웹 구현 단계: 필요한 단위·연결 테스트와 실제 사용자 흐름 확인으로 입력부터 화면까지 검증한다. 정상·비정상 상태를 구분하고 필수 저장·내보내기 결과는 다시 읽어 확인한다.

실행 검증은 기존 프로젝트의 진입점과 동일한 절차를 사용한다. 초기 데이터·상태, 필요한 버전·환경변수 이름, 정확한 명령·인자, 준비 완료 신호·관찰·정리 방법을 기록하고, 시간·난수·외부 의존성은 필요한 범위에서 고정한다. 검사 중 소스를 바꾸면 수정 후 다시 검증한다. 시간 초과·미실행·준비 실패를 성공으로 처리하지 않으며 정리할 때는 자신이 시작한 프로세스만 대상으로 한다.

## 데이터와 인프라 예외

실제 구조와 요구에 관련 있는 사례를 골라 기대 동작을 먼저 정한다. 모든 예외를 의무적으로 시험하지 않는다.

- 데이터: 빈 CSV, 필수 컬럼·값 누락, 형식·자료형 오류, 중복 식별자, 조인 불일치, 기간·시간대 경계, 분모 0, 허용 범위를 벗어난 값.
- 인프라: 파일 경로·읽기 권한 문제, 서버 시작·포트 연결 실패, 실제로 사용하는 API의 시간 초과·오류, 저장 실패, 재시작·새로고침 뒤 상태 유지, 관련 있는 중복 요청.

예외마다 어느 계층에서 감지하는지, 잘못된 값을 차단하는지, 사용자에게 무엇을 표시하는지, 마지막 정상 결과나 저장 상태를 보존하는지 확인한다. 필요한 실패는 격리된 시험 환경이나 대체 응답으로 재현한다. 외부 시스템을 실제로 중단시키거나 없는 장애를 시험했다고 주장하지 않는다. 허용된 도구로 확인할 수 없는 것은 미검증으로 남긴다.

## 수치의 독립 검증

출력 수치가 있는 경우 원본 CSV 파일·컬럼·대상 행 또는 필터 조건, 조인과 중복의 영향, 집계 단위·분모·분자·반올림을 확인한다. 구현과 별개의 손계산이나 단순한 별도 계산 경로로 기대값을 만들고 실제값·차이·필요한 허용 오차를 대조한다. 같은 업무 계산 함수를 재사용한 검사는 독립 검증으로 표시하지 않는다. 어떤 수치를 어떤 범위에서 확인했는지 기록한다.

## 검사가 오류를 잡는지 확인하기

정상·경계·불가 사례를 고르고 필요한 저장·재조회·중복 요청·오류 후 상태 보존까지 관찰한다. 기능을 복제하거나 무조건 성공하는 검사를 만들지 않는다. 핵심 검사의 신뢰성이 의심되면 대표 반례나 격리 복사본의 실제 규칙 위반으로 정상 통과 → 해당 규칙 때문에 실패 → 복구 후 통과를 같은 초기 상태·명령으로 확인한다. 문법 오류나 서버 시작 실패는 업무 로직의 탐지 근거가 아니다. 실패 증거와 복구 결과를 남기고 의도적 결함은 최종 코드에 남기지 않는다. 모든 변경에 결함 주입을 강제하지 않는다.

## 실제 규모와 개선 효과 확인

제공된 데이터 규모에서 핵심 조회·계산·화면 갱신의 소요 시간을 필요한 범위에서 확인한다. 같은 CSV의 반복 읽기, 중복 계산, 과도한 데이터 전달과 불필요한 화면 갱신 중 실제 병목을 측정하고, 그 근거와 수정 비용을 기준으로 개선 순서를 정한다.

개선 비교는 같은 입력·기간·조건으로 하고 관련 기존 동작도 다시 확인한다. 예측 과제는 과거 정보로 이후 시점을 검증하고 미래 정보를 섞지 않는다. 한도·중단·미기록 때문에 일부만 관측된 값을 곧바로 전체 규모로 해석하지 않는다. 추정·모의 값과 실측을 구분하고, 증명하지 않은 전역 최적이나 측정하지 않은 개선율을 주장하지 않는다.

## 기록과 실패 처리

WORKLOG.md 또는 동등 기록에 설계의 누락·모순 검토 결과와 요구 식별자, 정상·비정상 구분, 원자료·독립 기대값·실제값, 명령 또는 조작, 실행 대상, 상태와 남은 한계를 적는다. 관련 변경 후에는 영향받는 검증을 다시 실행한다. 실패하면 원인을 고치고 같은 사례로 재검증한다. 기대값을 근거 없이 낮추거나 실패 검사를 없애 통과시키지 않는다.

실제 화면을 확인하지 못했으면 화면 미검증이라고 기록한다. 정적 코드 확인·빌드·계산 테스트·화면 확인을 구분한다. 필수 요구와 관련 검증이 통과하면 새로운 근거 없이 검사를 반복하지 않는다.

## 근본 원인 디버깅

1. 기대 결과와 실제 결과를 구분하고 실제 사용자 진입점·최소 입력·고정 초기 상태로 실패를 재현해 증거를 남긴다.
2. 환경 준비 문제·검증기 오류·명세 불일치·제품 로직 오류를 구분하고, 로그·실제 값·호출 경로로 결과가 처음 어긋나는 지점을 찾는다. 같은 가설이 실패하면 재시도 전에 전제를 확인한다.
3. 확인된 원인을 필요한 범위에서 수정한다. 근거 없는 값 보정·재시도·예외 무시로 증상을 숨기지 않는다. 같은 오류 패턴의 관련 호출자나 저장 경로도 필요한 범위만 살핀다.
4. 수정 전 실패와 수정 후 성공을 같은 절차의 짧은 회귀 검사로 확인한다. 입력·원인 위치·수정 이유·실패한 가설·실제 결과·남은 한계를 기록하고, 확인하지 못한 원인은 가설로 남긴다.

## 단계 완료와 점검

확인된 동작과 미확인 범위, 남은 위험을 설명한다. 개선할 부분이 있으면 현재 한계와 대안·예상 효과·비용·같은 조건의 확인 방법을 연결하고 측정 전에는 개선됐다고 표현하지 않는다. 이해 점검 스킬로 검증 근거, 예외 동작, 개선을 확인할 방법 중 중요한 한 가지를 묻는다. 실제 제출과 AI 지원 종료 방식은 과제 안내를 따른다.
```

```markdown
# 아키텍처와 의사결정을 설명하는 이해 점검

## 입력과 결과

입력은 방금 완료한 단계, 실제 과제·데이터·설계·구현·검증 근거와 이전 사용자 답변이다. 결과는 사용자가 아키텍처와 데이터 기반 의사결정을 의식적으로 설명한 내용과 설명 가능·보완 필요·확인 불가·응답 대기 상태다. 아직 설계 중인 내용과 실제로 구현·실행한 동작을 구분한다.

## 한 번의 점검

1. 현재 단계의 중요한 판단·처리 경로·예외·수치 중 하나를 고르고 답을 확인할 문서·CSV의 행과 컬럼·코드·실행 근거를 확보한다. 아직 구현하지 않은 구조나 측정하지 않은 수치를 사실로 전제하지 않는다.
2. 실제 과제에 맞는 질문 한 개를 먼저 제시한다. 사용자가 질문 목록을 원하지 않는 한 여러 문제를 한꺼번에 내지 않는다. 답변 전에 모범답안이나 답이 그대로 드러나는 해설을 함께 제시하지 않는다.
3. 사용자 답변을 기다린다. 질문과 무관한 확정된 구현·검증은 계속할 수 있다. 사용자의 업무 결정이 필요한 부분은 답을 받기 전 확정하지 않는다.
4. 답변을 실제 근거와 대조해 맞는 부분 → 보완할 부분 → 확인 근거 순으로 짧게 피드백한다. 왜 그렇게 결정했고 어떻게 동작하는지, 정상과 예외를 구분하고 근거에 연결하는지를 본다. 내용이 맞으면 전문 용어나 표현을 불필요하게 문제 삼지 않는다.
5. 핵심 오해가 있으면 작은 실제 사례로 설명하고 자기 말로 다시 설명할 후속 질문 한 개를 한다. 해설 직후 따라 말한 것과 이후 독립적으로 설명한 것을 구분한다.

## 질문을 고를 관점

| 관점 | 실제 결과에 맞춰 물을 내용 |
| --- | --- |
| 데이터와 의사결정 | 어떤 행·컬럼·분포나 담당자 답변을 보고 이 규칙을 택했으며, 다른 선택 대신 이 방법을 고른 이유는 무엇인가? |

| 아키텍처 | 각 구성 요소는 왜 필요하며 어디서 계산·상태·저장을 책임지는가? 구성 하나를 바꾸면 어디에 영향이 생기는가? |

| 추가 개선 | 현재 한계나 측정한 병목을 줄일 대안은 무엇이며, 비용·기존 동작에 미치는 영향·개선 효과를 같은 조건에서 어떻게 확인할 것인가? |

질문은 한 판단이나 한 사례에 초점을 맞춘다. 존재하지 않는 서버·API·저장소를 전제하지 않는다. 수치 질문은 실제 출력된 값 하나를 선택하고 구현 코드의 결과를 다시 읽은 것을 독립 검증이라고 인정하지 않는다. 설계상의 예상 예외 동작과 실제 재현·검증한 동작을 구분해 설명하게 한다.

한 번의 점검은 질문 하나와 짧은 피드백으로 마친다. 답이 충분하면 다음 단계로 진행한다. 사용자 응답이 없으면 응답 대기로 남기고, 설명 자료를 제공한 것만으로 이해했다고 표시하지 않는다. 나중에 점검하자는 요청은 보류로 기록한다.

자료에 접근할 수 없으면 확인 불가로 남기고 일반 연습 질문임을 밝힌다. 공식 문제·배점·합격 여부를 예측하지 않는다. 실제 후속 서술형 등 AI 지원이 종료되는 시점 이후에는 연습을 계속하거나 답변을 대신 만들지 않는다. 정확한 종료 경계는 해당 과제 안내로 확인한다.
```

```markdown
# 인계와 재개

## 입력과 결과

입력은 실제 과제·파일·Git 상태, 요구·결정 기록, 실행·검증 근거와 미결 질문이다. 결과는 다음 세션이 현재 상태를 확인하고 바로 이어갈 수 있는 handoff.md다. 기존 docs/handoff.md 등 동등 문서가 있으면 재사용한다. 인계 문서 작성과 실제 검증·커밋·제출·전달을 구분한다.

## 인계를 남길 때

- 현재 목표·마지막 요구 변경, 작업 경로·브랜치·확인한 직전 SHA·미커밋 변경을 실제 상태에서 확인한다. Git이 없으면 없다고 적는다.
- 주요 구조·입출력·데이터와 저장 위치, 중요한 결정과 이유는 PRD.md·WORKLOG.md·EXPLAIN.md의 해당 위치를 연결한다. 긴 설명을 복제하지 않는다.
- 초기화·시작·검증의 정확한 명령, 필요한 환경변수 이름, 실제 포트·준비 상태, 증거 파일 경로를 남긴다. 임시 자료가 사라질 수 있으면 재생성 방법을 적는다.
- 실제 통과 범위와 실패·미실행·수동 확인·남은 위험, 답변이 필요한 DM과 이해 점검의 응답 대기를 구분한다.
- 다음 세션이 바로 할 명령 또는 수정 한 가지와 필요한 선행 조건을 남긴다. 유지해야 할 서버·상태와 정리한 임시 자원을 구분하고, 정리할 때는 자신이 만든 것만 대상으로 한다.

마지막 확인 전에 인계 초안을 준비하고 확인 후 실제 결과만 갱신한다. 검증 전 성공을 미리 적지 않는다. 자기 자신을 포함할 최종 커밋 SHA를 문서에 넣는 순환을 만들지 않는다. 커밋이나 제출은 요청과 실제 과제 규칙에 따르며, 인계 스킬이 자동으로 수행하지 않는다.

## 인계를 받을 때

1. 실제 과제 안내·RULE.md·적용되는 지침과 인계, 연결된 요구·검증 기록을 읽는다.
2. 현재 파일·Git 상태·최근 변경과 증거 파일의 실제 내용·존재 여부를 대조한다. 이전의 성공 문장만으로 현재 동작을 통과 처리하지 않는다.
3. 달라진 환경·초기 상태를 확인하고 필요한 핵심 흐름을 기록된 절차로 재검증한다. 과거 조사와 유효한 근거는 재사용한다.
4. 미결 조건을 임의 확정하거나 응답 대기를 이해 완료로 바꾸지 않는다. 확인된 다음 작업부터 이어가고 달라진 사실만 갱신한다.

외부 서비스로 인계를 전송하거나 세션을 새로 생성하지 않는다. 과제와 관련 없는 개인 대화·설정을 인계 자료에 넣지 않는다.
```

## 6. 시작·재개·마무리 때 확인할 것

- 시작: 실제 안내와 데이터 → 가장 큰 미확인 조건 → 첫 번째 작동 흐름을 정한다.
- 진행: 한 번에 필요한 스킬을 읽고, 핵심 단계마다 설계 검증·로직 및 동작 검증·근거 기록·역질문을 반복한다.
- 변경: 새로운 답변이나 실패 근거가 나온 부분의 요구·설계·코드·검사를 함께 바꾼다.
- 전환·중단·재개: cofa-handoff로 실제 상태·증거·미결 질문·응답 대기와 다음 작업을 인계하고 확인한다.
- 마무리: 실행 방법, 충족한 요구, 실제 검증 결과, 데이터부터 화면까지의 흐름, 판단 이유, 정상·예외 동작, 수치의 독립 검증 근거, 남은 한계와 개선 방법·이해 점검 상태를 정리한다. 실제 제출 절차와 AI 지원 종료 시점은 과제 안내를 따른다.
