# Astra 3개 독립 E2E와 최종 재검증

## 수행 방식

사용자가 요청한 gpt-6-astra 에이전트 3개를 각각 새 맥락으로 시작했다. 이전 대화 없이 같은 공개 버전 c1045e32308fd292a01696406973e5912a442a9c와 서로 다른 과제 문서만 읽었다. 각자 독립 소스 복사본과 빈 Git 프로젝트에 키트를 설치하고 앱·검사·맵·의도·판단·인계를 직접 작성했다.

이는 준비 단계 평가다. RULE.md의 실전 Astra 제한을 바꾸지 않는다.

|---|---|---|---|---|---|
| CLI 장부 | a2b0e2ac | 중복 출금으로 잔액 70 대신 40, 커밋 실패·HEAD 유지 | U002의 두 번째 시도 | 확인 | eee94fac |

각 평가의 원본 보고서·구조화 결과·부모의 Git/실행 증거 대조는 [장부](astra/ledger/report.md), [예약](astra/reservation/report.md), [집계](astra/orders/report.md)에 있다. 부모는 소스 SHA·깨끗한 작업트리·공통 실행기 미변경·훅 연결·성공과 실패의 실제 실행 보고서를 직접 확인했다.

## 같은 맥락으로 이해했는가

세 평가자가 각자 답한 12개 항목을 전문 읽고 실제 산출물과 비교했다.

| 항목 | 공통 이해 |
|---|---|
| 범위 | 앱은 별도 구현하고 공통 절차·검증·기능 맵·로컬 커밋을 재사용 |
| 진입점 | fde-workflow와 앱별 verify-app |
| 읽기 순서 | 과제 안내·README → RULE → AGENTS → 안내·protocol → 기존 의도/인계와 실제 상태 |
| 기능 맵 위치 | .agents/skills/verify-app/features/F ID별 파일과 생성 인덱스 |
| 맵 갱신 | map add → map sync → map check, 같은 기능은 같은 ID |
| 커밋 조건 | begin → 전체 stage → diff 확인 → commit → iterate --staged |
| 반복 주체 | 에이전트가 원인 수정, 실행기는 한 차례 검사·예산·결과 기록 |
| 증거 | .kit/runs 및 KIT_RUN_DIR, 다음 실행이 이전 증거를 대체하지 않음 |
| stage | 부분 stage 금지 |
| 모델 | 실전 허용 Codex만, 준비 Astra 평가와 구분 |
| 화면 | 에이전트 화면 자동조작 금지, API 성공과 화면 성공 구분 |
| 인계 | 실제 상태·명령·결과·증거·한계·다음 행동을 기록하고 재개 시 확인 |

원문 답변은 [맥락 비교 자료](astra/context-comparison.json)에 보존했다. 동일한 코드를 산출한다는 의미는 아니다. 앱의 HTTP 경로·JSON 키·경계 정책은 실제 과제 요구로 정하고, 지정되지 않았다면 구현 전에 의도·판단 기록에 고정한다. 이번 서로 다른 세 과제에서는 공통 실행 방법과 맵 구조가 일치했다.

## 발견한 누락과 반영

| 발견 | 실제 영향 | 반영 |
|---|---|---|
| 설치 시 helper 실행권한 손실 | 새 프로젝트의 원본 helper가 직접 실행되지 않을 수 있음 | 설치기가 원본 일반 권한 비트 보존, 설치·재설치 회귀 검사 |
| 예약 환경변수 안내 누락 | 올바른 환경 고정을 시도해도 검사 전 거절되고 원인 이름이 안 나옴 | 예약 목록 문서화, 오류에 충돌 변수 이름 표시, 회귀 검사 |
| doctor 출력 의미 혼동 | 구성 PASS를 실제 포트·환경 준비로 오해 가능 | 구조·설정 점검임을 출력·도움말·문서에 명시, 실제 환경은 check에서 확인 |
| cleanup 범위의 포괄적 표현 | 앱 실행 전 거절도 cleanup이 실행됐다고 읽을 수 있음 | 사전검사에서는 앱과 cleanup을 시작하지 않는 경계를 명시 |
| 새 세션의 환경 변화 | 파일 지문이 같아도 실행 환경은 달라질 수 있음 | 재개 시 status만 보지 않고 실제 check를 다시 실행하도록 명시 |
| 재실행 보조 도구의 실패 증거 수명 | 임시 프로젝트 제거로 실패 로그를 잃을 수 있음 | 성공·실패 모두 replay-evidence에 실제 산출물 보관 |

## 최종 확인과 재현

보완 후 공통 실행기 통합 검사 17개가 통과했다. [실제 테스트 출력](kit-tests.txt)을 확인한다.

부모가 현재 키트로 합성 예제 세 개를 각각 새 Git 프로젝트에 설치하고 실제 pre-commit 커밋을 수행했다. 세 예제 모두 PASS이며 결과는 [최종 재실행 자료](example-replay.json), 실제 로그·앱 산출물은 replay-evidence/에 보존했다. 이 자료의 kit_sha256은 검사한 실제 실행기와 연결된다.

~~~sh
python3 scripts/audit_sources.py
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -v
python3 scripts/replay_examples.py all
~~~

최초 제한 샌드박스에서는 HTTP 소켓 bind가 PermissionError로 실패했고 전체 검사가 정확히 차단했다. 로컬 서버 실행 권한이 허용된 준비 환경에서 세 예제를 다시 실제 실행하여 통과했다. 실제 응시 환경의 제약을 우회하라는 지침이 아니다.

## 남는 과제별 작업

앱의 구현과 검증 명령, 초기 데이터, 불변식, UI 수동 확인 범위, 성능 기준과 제출 조건은 문제가 주어진 뒤 채워야 한다. 이 키트는 보안 샌드박스·전수 취약점 탐지·형식 증명·모든 미래 과제의 정확성을 제공하지 않는다.

동시성·장애 복구·실제 부하·모든 플랫폼 버전은 이번 세 시나리오의 검증 범위 밖이다. 과제에서 필요하면 별도의 인수 조건과 실제 검사를 추가한다. 원본 pstack 전체 코드와 모든 선택 도구를 실행했다고 주장하지 않는다.
